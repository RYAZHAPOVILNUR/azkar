# ТЗ: большой достоверный движок азкаров для Azkar Mini App

## 1. Цель

Сделать в `@azkarnurtechbot` и Mini App `azkar.nurtech.dev/app` не просто экран утренних и вечерних азкаров, а полноценную библиотеку достоверных азкаров на все случаи жизни.

Продуктовая цель:

- пользователь открывает приложение и находит азкар для любой ситуации;
- каждый текст имеет арабский оригинал, русский перевод, транскрипцию, источник, степень достоверности и повторения;
- слабые и сомнительные тексты не смешиваются с достоверными;
- база расширяется через проверяемый контентный pipeline, а не через ручное редактирование `miniapp/index.html`;
- приложение остаётся быстрым и удобным в Telegram Mini App.

Главная идея: строим не "ещё одну копию Хиснуль Муслим", а проверяемую базу азкаров с источниками и статусами верификации.

## 2. Принцип достоверности

Контент допускается в основную библиотеку только при понятной цепочке происхождения:

- Коран;
- хадисы из Бухари и Муслима;
- достоверные или хорошие хадисы из других сборников;
- тексты, оценённые как достоверные/хорошие у шейха аль-Альбани;
- тексты из проверенных салафитских сборников азкаров;
- тексты, уже сверенные по текущему источнику проекта.

Нельзя:

- добавлять азкар без источника;
- брать текст из неизвестного сайта без сверки;
- доверять OCR арабского текста без ручной проверки;
- копировать чужие приложения напрямую;
- смешивать слабые хадисы с основными азкарами;
- менять религиозный текст ради "красоты" или UX.

Каждая единица контента получает один из статусов:

```txt
verified                 полностью проверено
needs_review             импортировано, нужна проверка
needs_arabic_review      нужно сверить арабский текст
needs_translation_review нужно сверить русский перевод
needs_source_review      нужно сверить источник и степень
duplicate_candidate      вероятный дубль
excluded_weak            исключено из-за слабости/сомнительности
copyright_blocked        нельзя публиковать полный текст из-за прав
```

## 3. Главные источники

### 3.1. Текущий источник проекта

В README проекта уже указан источник:

```txt
content/raslan-source.pdf
```

Книга шейха Мухаммада ибн Саида Расляна:

```txt
أذكار الصباح والمساء من صحيح السنة المطهرة
```

Использование:

- оставить как сильный источник для утренних и вечерних азкаров;
- не менять текущие утренние/вечерние тексты без сверки;
- при переносе в новый движок пометить как `collector_source: raslan_morning_evening`.

### 3.2. Хиснуль Муслим / Крепость мусульманина

Автор: Саид ибн Али ибн Вахф аль-Кахтани.

Назначение:

- базовая структура "на все случаи жизни";
- категории: сон, пробуждение, одежда, дом, мечеть, еда, путешествие, болезнь, тревога, истихара и т.д.;
- хороший старт для полного каталога.

Источник для исследования:

- https://islamhouse.com/en/books/2819940/

План:

- использовать как структурный каркас категорий;
- импортировать тексты как `needs_review`;
- сверить арабский и источники;
- русский перевод использовать только после проверки прав или заменить собственным переводом/редакцией.

### 3.3. Сахих аль-Азкар

Название:

```txt
Сахих аль-Азкар = Слова поминания Аллаха из достоверных хадисов
```

Составитель: Абу-ль-Хасан Мухаммад бин Хасан аш-Шайх.

Основа: азкары из достоверных хадисов, отобранные из трудов шейха Мухаммада Насируддина аль-Альбани.

Русский перевод: Абдулла Нирша.

Источники:

- https://musulmanin.com/sahih-al-azkar-elektronnaya-versiya.html
- https://archive.org/download/SahihAlAzkar-IslamicRussianBook.pdf/SahihAlAzkar-IslamicRussianBook.pdf

Почему важно:

- это один из лучших источников под задачу "саляфитски достоверные азкары";
- можно получить много азкаров на разные случаи;
- в книге есть источники и краткие пояснения.

План:

- скачать PDF в `content/azkar-db/raw/sahih-al-azkar/`;
- извлечь текст;
- разметить главы;
- распознать арабский, перевод, источник, комментарии;
- всё импортировать со статусом `needs_review`;
- первые 100 важных карточек проверить вручную и выпустить в `verified`.

Важно по правам:

- проверить возможность публикации полного русского перевода;
- если права неясны, использовать книгу как источник сверки, а перевод делать собственный/редакционный.

### 3.4. al-Kalim at-Tayyib / Sahih al-Kalim at-Tayyib

Автор базовой книги: Ибн Таймия.

Проверенная версия: отбор/тахкык шейха аль-Альбани.

Использование:

- дополнительный корпус;
- особенно для достоинств зикра, ежедневных поминаний, дуа и защиты;
- использовать после MVP, когда уже готов pipeline.

### 3.5. QuranEnc

API:

- https://quranenc.com/en/home/api/

Использование:

- дуа из Корана;
- русские переводы смыслов;
- ссылки на суры/аяты;
- возможное получение footnotes.

Условия:

- не изменять перевод;
- указывать источник QuranEnc;
- указывать версию;
- сохранять информацию о переводе;
- сообщать источнику о найденных ошибках.

### 3.6. HadeethEnc

API:

- https://hadeethenc.com/api-docs/

Использование:

- сверка хадиса;
- перевод хадиса;
- краткое объяснение;
- категории;
- степень достоверности;
- ссылки на хадис.

### 3.7. Sunnah.com

API:

- https://sunnah.com/developers

Особенности:

- нужен API key;
- доступна только часть данных;
- можно запросить ключ через GitHub issue;
- использовать как дополнительную сверку, не как единственный источник.

### 3.8. Life With Allah / Dhikr & Dua

Источник:

- https://play.google.com/store/apps/details?id=com.alifewithallah.app

Использование:

- только как продуктовый benchmark;
- не копировать контент без разрешения;
- смотреть UX: 500+ дуа, перевод, транслитерация, source/virtue, audio, reminders, counter.

## 8. Контентный pipeline

### 8.1. Импорт

Каждый источник импортируется отдельно:

```bash
node scripts/azkar/import-current.mjs
node scripts/azkar/import-hisnul-muslim.mjs
node scripts/azkar/import-sahih-al-azkar.mjs
node scripts/azkar/import-quranenc.mjs
node scripts/azkar/import-hadeethenc.mjs
```

Все импорты по умолчанию создают `needs_review`, кроме уже проверенных текущих азкаров.

### 8.2. Нормализация

```bash
node scripts/azkar/normalize.mjs
```

Нормализация:

- единый формат арабского текста;
- удаление лишних переносов;
- нормализация пробелов;
- создание `arabic_search`;
- нормализация русских кавычек и апострофов;
- единые названия сборников;
- единый формат повторений.

### 8.3. Поиск дублей

```bash
node scripts/azkar/detect-duplicates.mjs
```

Искать дубли по:

- одинаковому арабскому тексту без харакатов;
- близкому русскому переводу;
- одинаковому источнику хадиса;
- похожему названию категории.

Результат:

```txt
content/azkar-db/reports/duplicates.md
```

### 8.4. Валидация

```bash
node scripts/azkar/validate.mjs
```

Проверки:

- есть `id`;
- `id` уникальный;
- есть `arabic`;
- есть `translation_ru` или `translation_missing: true`;
- есть хотя бы один `source_ref`;
- есть хотя бы одна категория;
- `repeat` положительный;
- все `category_ids` существуют;
- все `collection_ids` существуют;
- нет публикации `needs_review` в production export без флага;
- нет битых аудио-ссылок;
- нет пустых источников;
- нет случайного OCR-мусора.

### 8.5. Отчёт

```bash
node scripts/azkar/report.mjs
```

Пример отчёта:

```txt
Всего записей: 612
Verified: 184
Needs review: 301
Needs Arabic review: 74
Needs translation review: 127
Excluded weak: 18
Duplicate candidates: 77
No source: 0
No category: 0
With audio: 52
```

### 8.6. Export в Mini App

```bash
node scripts/azkar/export-miniapp.mjs
```

Создаёт:

```txt
miniapp/data/azkar.v1.json
miniapp/data/categories.v1.json
miniapp/data/collections.v1.json
miniapp/data/search-index.v1.json
```

Production export по умолчанию включает только:

```txt
verified
```

Можно добавить dev-флаг:

```bash
node scripts/azkar/export-miniapp.mjs --include-drafts
```

```js
const AZKAR_STORE = {
```

```js
async function loadAzkarDb() {
  const [items, categories, collections, search] = await Promise.all([

}
```

Если загрузка не удалась:

- показать экран ошибки;

## 10. Поиск

Поиск должен работать офлайн.

Индекс:

```json
{
  "id": "sleep_001",
  "tokens": [
    "сон",
    "перед сном",
    "аят аль курси",
    "защита",
    "بسم",
    "الكرسي"
  ]
}
```

Нормализация:

- lower-case;
- `ё` -> `е`;
- убрать арабские харакаты;
- убрать лишние символы;
- нормализовать апострофы;
- искать по частичному совпадению;
- поддержать арабский ввод.

Результат поиска:

```txt
Название
Категория
Первое совпадение в переводе/арабском
Бейдж источника
```

## 11. Аудио

Не обязательно сразу записывать всё, но модель заложить с первого релиза.

Структура:

```txt
miniapp/assets/audio/azkar/
  morning_001.mp3
  sleep_001.mp3
```

Возможности:

- play/pause;
- повторить N раз;
- скорость 0.75 / 1 / 1.25;
- автопереход к следующему;
- слушать всю категорию;
- кешировать последний загруженный аудио.

MVP:

- аудио для 30-50 самых важных азкаров;
- остальные показывают "аудио скоро".

## 12. Режим заучивания

Сильная функция для продукта.

Режимы:

1. Полный текст.
2. Скрыть перевод.
3. Показывать арабский по строкам.
4. Скрыть часть слов.
5. Проверка: пользователь читает, потом раскрывает.

Состояния:

```txt
new
learning
review
memorized
```

Локальное хранение:

```txt
azkar_memorization_state
```

Синхронизация через Telegram CloudStorage, если уже используется.

## 13. Статистика

Считать:

- сколько азкаров прочитано сегодня;
- сколько повторений;
- серии дней;
- утро/вечер отдельно;
- какие категории читаются чаще;
- прогресс по заучиванию.

Не делать статистику греховной/давящей. Формулировки мягкие:

```txt
Сегодня прочитано
Серия
Повторено
В заучивании
```

## 14. UX и дизайн

Ориентир по референсам:

- сетка категорий;
- крупные карточки;
- тёмная тема;
- быстрый доступ к утро/вечер/сон;
- продолжить чтение;
- избранное;
- поиск.

Но дизайн должен быть чище:

- не перегружать иконками;
- много воздуха;
- арабский текст — главный;
- источники видны, но не кричат;
- статусы достоверности аккуратными бейджами.

Главная структура:

```txt

Утро / Вечер / После намаза / Сон
Все азкары
Коллекции
Избранное
Поиск
Коран
Кибла
Настройки
```

## 15. Работа с правами

Нужно завести таблицу источников:

```txt

title
url
license
can_republish_arabic
can_republish_translation
attribution_required

```

Правила:

- если лицензия неясна, не публиковать полный перевод без решения;
- можно использовать источник для сверки и сделать собственный перевод;
- всегда указывать источник;
- для QuranEnc соблюдать их условия.

Не начинать с "давайте накидаем 500 азкаров".

## 20. Важное уточнение по продукту

Это приложение должно быть не просто "много азкаров".

Если просто добавить 500 текстов, получится тяжёлая библиотека, в которой новичок потеряется. Сильный продукт должен одновременно решать две задачи:

1. Дать полный каталог для тех, кто ищет конкретную мольбу.
2. Провести новичка по простому ежедневному пути.

Поэтому внутри приложения нужны два режима:

```txt
Простой режим
- Утро
- Вечер
- После намаза
- Перед сном
- Истихара
- Рукъя
- Поиск

Полная библиотека
- Все категории
- Все коллекции
- Все источники
- Расширенные фильтры
```

По умолчанию пользователь видит простой режим. Полная библиотека доступна через отдельную кнопку "Все азкары".

Так приложение не станет перегруженным, но останется мощным.

## 23. Review workflow

Каждая запись проходит путь:

```txt
imported
  -> normalized
  -> duplicate_checked
  -> arabic_checked
  -> source_checked
  -> translation_checked
  -> product_ready
  -> verified
```

В данных это можно хранить так:

```json
{
  "review": {
    "imported": true,
    "normalized": true,
    "duplicate_checked": true,
    "arabic_checked": false,
    "source_checked": true,
    "translation_checked": false,
    "product_ready": false,
    "verified": false,
    "reviewers": {
      "arabic": null,
      "source": "manual",
      "translation": null
    },
    "notes": [
      {
        "type": "translation",
        "text": "Нужно сверить термин 'فضل' в контексте.",
        "created_at": "2026-07-13"
      }
    ]
  }
}
```

Правило:

```txt
В production export попадает только verified=true.
```

Исключение возможно только для уже существующих текущих азкаров, если они ранее были утверждены владельцем и источником проекта.

## 24. Что делать, если источники расходятся

Будут ситуации:

- один источник даёт одну формулировку;
- другой источник даёт вариант;
- разные оценки хадиса;
- перевод отличается;
- повторения отличаются.

Нужна политика.

### 24.1. Разные формулировки арабского

Решение:

- не склеивать автоматически;
- хранить как варианты `variant_group_id`;
- показывать один основной вариант;
- остальные варианты доступны в "Другие версии".

Пример:

```json
{
  "variant_group_id": "sleep_last_words",
  "variant_role": "primary"
}
```

### 24.2. Разные степени достоверности

Решение:

- хранить все оценки;
- показывать наиболее осторожную формулировку;
- не публиковать спорное как `verified`, пока не принято решение.

Пример:

```json
"grade_refs": [
  { "grader": "al-Albani", "grade": "sahih" },
  { "grader": "at-Tirmidhi", "grade": "hasan" }
]
```

В UI:

```txt
Хасан / достоверность подтверждена в источниках
```

### 24.3. Разные переводы

Решение:

- русский перевод делать единым редакционным стилем;
- хранить источник перевода;
- если перевод QuranEnc, не менять его;
- если собственный перевод, пометить `translation_source: editorial`.

### 24.4. Разные повторения

Решение:

- хранить повторение как часть источника;
- если повторение установлено хадисом, показывать точно;
- если в сборнике повторение практическое, пояснить.

## 25. Версионирование базы

База должна иметь версию.

Файл:

```txt
miniapp/data/manifest.json
```

Пример:

```json
{
  "db_version": "2026.07.13.1",
  "generated_at": "2026-07-13T12:00:00+06:00",
  "items_count": 184,
  "verified_count": 184,
  "min_app_version": 1,
  "files": {
    "azkar": "azkar.v1.json",
    "categories": "categories.v1.json",
    "collections": "collections.v1.json",
    "search": "search-index.v1.json"
  }
}
```

Зачем:

- понимать, какая база у пользователя;
- чистить кеш при обновлении;
- отлаживать ошибки;
- показывать "база обновлена".

## 26. Кеширование и офлайн

Telegram Mini App должен работать быстро.

Стратегия:

1. При первом открытии загрузить manifest.
2. Проверить версию в `localStorage`.
3. Если версия новая, скачать JSON.
4. Сохранить в IndexedDB или localStorage, если размер позволяет.
5. При следующем открытии показывать кеш сразу.
6. В фоне проверить обновление.

Для MVP можно localStorage, но для большой базы лучше IndexedDB.

Псевдологика:

```js
async function initAzkarDb() {
  const cached = await loadCachedDb();
  if (cached) renderFromDb(cached);

  const manifest = await fetchManifest();
  if (!cached || cached.version !== manifest.db_version) {
    const fresh = await fetchDbFiles(manifest);
    await saveCachedDb(fresh);
    renderFromDb(fresh);
  }
}
```

Если сети нет:

```txt
Показать последнюю сохранённую базу.
Если базы нет — показать ошибку с кнопкой "Обновить".
```

## 27. Производительность

Риски:

- 500+ азкаров могут раздуть JSON;
- поиск может тормозить;
- арабские шрифты тяжёлые;
- аудио может занимать много места;
- Telegram WebView слабее обычного браузера.

Решения:

### 27.1. Разделить данные

Не грузить всё сразу, если база станет большой.

Вариант MVP:

```txt
azkar.v1.json              все verified азкары
```

Вариант V2:

```txt
azkar-core.v1.json         утро/вечер/после намаза/сон
azkar-categories.v1.json   список категорий
azkar-full.v1.json         полная библиотека по требованию
```

### 27.2. Lazy load

- главная грузит core;
- поиск грузит search-index;
- полная категория грузит full db;
- аудио грузится только по нажатию.

### 27.3. Виртуализация списков

Если категория содержит много записей:

- рендерить только видимые карточки;
- либо пагинация "показать ещё";
- не вставлять 500 DOM-карточек сразу.

### 27.4. Размеры

Целевые ограничения:

```txt
core JSON до 250 KB gzip
full JSON до 1.5 MB gzip
search index до 300 KB gzip
initial render до 1 секунды на среднем телефоне
```

## 28. Безопасность и приватность

Что можно хранить:

- избранное;
- прогресс;
- статистику чтения;
- настройки;
- последнюю открытую категорию.

Что нельзя отправлять наружу без явного решения:

- точную геолокацию;
- личные заметки;
- историю чтения на сервер;
- данные Telegram пользователя, кроме необходимого для бота.

Если будет синхронизация:

- использовать Telegram CloudStorage;
- хранить только минимальные ключи;
- не хранить чувствительные религиозные заметки на своём сервере без необходимости.

## 30. Транскрипция

Транскрипция полезна новичкам, но есть риск ошибок.

Правила:

- транскрипция не заменяет арабский;
- в UI писать "транскрипция приблизительная";
- не пытаться автоматически транскрибировать всё без проверки;
- для важных азкаров сделать ручную транскрипцию;
- дать возможность отключить транскрипцию.

Статус:

```json
"translit": {
  "ru": "Аллахумма...",
  "status": "reviewed",
  "note": "Приблизительная передача для помощи новичкам"
}
```

## 31. Перевод

Нужен единый русский стиль.

Правила:

- кратко;
- без канцелярита;
- без добавления смысла от себя;
- квадратные скобки использовать только если нужно пояснить скрытый смысл;
- имена Аллаха переводить осторожно;
- не менять переводы QuranEnc, если они используются как источник.

Поля:

```json
"translation": {
  "ru": "...",
  "source": "editorial",
  "review_status": "needs_review"
}
```

Важно:

- подборка может включать азкары из разных категорий;
- один азкар может быть в нескольких подборках;
- подборка не должна утверждать то, чего нет в источнике.

## 34. Порядок отображения

Нужен явный порядок:

1. То, что приходит из Корана.
2. То, что приходит из Бухари/Муслима.
3. Часто используемые азкары.
4. Короткие перед длинными для новичка.
5. По порядку книги, если пользователь открыл коллекцию.

В данных:

```json
"order": {
  "category": 10,
  "collection": 42,
  "beginner": 3
}
```

## 35. Миграция текущего приложения

Важно не переписать всё за раз.

### 35.1. Шаг 1: snapshot текущего состояния

Сохранить текущий `AZKAR` как:

```txt
content/azkar-db/raw/current-miniapp/azkar.current.json
```

### 35.2. Шаг 2: конвертация

Скрипт:

```bash
node scripts/azkar/import-current.mjs
```

Делает:

- читает текущий массив;
- создаёт normalized JSON;
- сохраняет старые id/progress совместимыми.

### 35.3. Шаг 3: совместимость прогресса

Сейчас прогресс может быть привязан к старым ключам.

Нужно сделать mapping:

```json
{
  "morning:0": "morning_001",
  "morning:1": "morning_002"
}
```

Чтобы у пользователей не пропали избранное и прогресс.

### 35.4. Шаг 4: fallback

На время миграции оставить fallback:

```txt
Если JSON не загрузился, использовать встроенный минимальный core.
```

Но после стабилизации убрать большой встроенный массив.

## 36. Риски

### 36.1. Риск: неправильный религиозный текст

Митигировать:

- review statuses;
- production только verified;
- отчёт перед экспортом;
- ручная сверка арабского.

### 36.2. Риск: нарушение прав на перевод

Митигировать:

- таблица лицензий;
- не публиковать спорные переводы;
- делать собственную редакцию;
- запрашивать разрешения.

### 36.3. Риск: приложение станет тяжёлым

Митигировать:

- core/full split;
- lazy load;
- gzip/brotli;
- кеш;
- виртуализация.

### 36.4. Риск: новичок потеряется

Митигировать:

- простой режим;
- "Минимум на день";
- подборки;
- аккуратная главная.

### 36.5. Риск: дубли

Митигировать:

- duplicate detector;
- variant groups;
- collection refs.

### 36.6. Риск: разные мнения по достоверности

Митигировать:

- хранить все оценки;
- спорное держать в `needs_source_review`;
- не показывать как verified до решения.

## 37. Вопросы, которые нужно решить до разработки

### 37.1. Какие переводы можно публиковать?

Нужно отдельно проверить:

- `Сахих аль-Азкар`, перевод Нирши;
- русские издания Хиснуль Муслим;
- тексты IslamHouse;
- условия QuranEnc;
- условия HadeethEnc.

Решение:

```txt
Если право неясно, не публикуем полный перевод как "взято из книги".
Делаем собственный перевод/редакцию и указываем источник хадиса.
```

### 37.2. Кто будет религиозным reviewer?

Без этого нельзя массово выпускать 500 карточек.

Минимальный вариант:

- разработчик импортирует;
- владелец/знающий брат сверяет топовые карточки;
- спорное остаётся скрытым.

### 37.3. Нужна ли транскрипция для всех?

Варианты:

1. Да, но только reviewed.
2. Только для топовых.
3. Автоматическая с пометкой "не проверено".

Рекомендация:

```txt
Для MVP: транскрипция только для топовых и текущих азкаров.
Для полной базы: добавлять постепенно.
```

### 37.4. Нужен ли русский шарх для всех?

Рекомендация:

```txt
Нет. Для всех нужен источник.
Шарх нужен для топ-100 и сложных мест.
```

### 37.5. Нужны ли слабые хадисы отдельным режимом?

Рекомендация:

```txt
Нет для MVP.
Ценность продукта именно в достоверности.
```

### 37.6. Сколько азкаров выпускать в первый релиз?

Рекомендация:

```txt
Не гнаться за числом.
Лучше 150 verified, чем 600 сомнительных.
```

Но импортировать можно больше в draft.

## 39. Критерии качества контента

Каждая опубликованная карточка должна отвечать на вопросы:

```txt
Что читать?
Когда читать?
Сколько раз читать?
Откуда это пришло?
Насколько это достоверно?
Что это значит по-русски?
Можно ли это быстро найти?
```

Если хотя бы один вопрос без ответа, запись не должна идти в `verified`, кроме редких случаев, где это явно допустимо.

## 40. Финальное видение

Идеальный результат:

- приложение открывается быстро;
- новичок сразу понимает, что читать утром/вечером;
- ищущий человек находит азкар для ситуации;
- каждый текст имеет источник;
- слабое не попадает в основную базу;
- можно читать по книгам;
- можно читать по ситуациям;
- можно учить;
- можно слушать;
- можно делиться;
- можно доверять.

Это и есть отличие от обычных приложений: не просто много карточек, а понятная, проверенная и удобная система поминаний.
